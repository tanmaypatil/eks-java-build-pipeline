Ephemeral EKS Java build pipeline: architecture

How a run works from start to finish: creating the cluster, running the orchestrator, detecting the Java version, the build Job, the report, the cost forecast, and the planned experiments that optimise build time. Every section links to the file that implements it.

1The whole run

One command, bin/all.sh, runs four phases. Your laptop, or any machine with AWS credentials, only drives the run. Every Java build happens inside the cluster.

The flow from your terminal:

bin/all.sh
  trap teardown EXIT INT TERM          # teardown is guaranteed from here on
  stamp up_start  -> bin/up.sh  -> stamp up_end
  bin/run.sh                           # stamps run_start, builds_end, run_end
  (exit) -> stamp down_start -> bin/down.sh -> stamp down_end -> report re-rendered with real teardown time

Each stamp appends phase=epoch_seconds to runs/<RUN_ID>/phases.env. Those timestamps feed the measured cost in section 8.

2Cluster lifecycle built

Files: bin/up.sh, bin/down.sh, bin/leftovers.sh, settings in config/run.env.

Creation (bin/up.sh)

  1. Pick the Kubernetes version. With K8S_VERSION=auto, it calls aws eks describe-cluster-versions --version-status STANDARD_SUPPORT and takes the newest. A version in extended support bills the control plane at $0.60/h instead of $0.10/h, so this check protects the budget.
  2. Render an eksctl ClusterConfig as a heredoc and run eksctl create cluster -f. eksctl creates two CloudFormation stacks: the cluster (VPC, subnets, IAM roles, control plane) and the node group.
  3. Point kubectl at the cluster with aws eks update-kubeconfig.
  4. Apply the jbp-gp3 StorageClass, so the workspace PVC gets an EBS gp3 volume.

If a cluster with that name already exists, up.sh reuses it. That makes --keep plus repeated runs cheap.

What gets created, and why each choice

PieceChoiceWhy
Control planeEKS, newest standard-support versionSame managed Kubernetes as production EKS; close to OpenShift for Job/Pod semantics. $0.10/h.
Networkingeksctl VPC, nat.gateway: Disable, nodes in public subnetsA NAT gateway costs ~$0.045/h plus $0.045/GB. With public subnets, nodes reach GitHub, Maven Central and the image registries directly through a public IPv4 ($0.005/h).
Nodes1 managed node group, spot: true, AL2023, 6 instance types of the 4 vCPU / 16 GiB classSpot is ~60-70% cheaper than on-demand. Listing several types lets AWS pick whichever pool has capacity. One node is enough because builds run one at a time and the PVC is single-node anyway.
Node disk40 GB gp3Fits the build images (~0.5 GB each, up to 4-5 per run) with room to spare.
Storageaws-ebs-csi-driver add-on, IRSA via wellKnownPolicies.ebsCSIControllerNeeded for a PVC on EKS. OIDC lets the driver's pod assume an IAM role without node-wide permissions.
LoggingControl-plane logs off (eksctl default)CloudWatch ingestion costs money and we don't need it.
Tagsproject=java-build-perf, jbp-ephemeral=true; EBS volumes get jbp-cluster=<name>Lets you find leftovers and attribute cost.

Why not Karpenter? Karpenter is great for long-lived clusters with changing load. Installing it adds a Helm release, IAM roles, an SQS queue for interruptions and a few minutes per run. For a cluster that lives an hour with a fixed node count, a managed spot node group gives the same price with fewer moving parts. It can come back once runs need several node sizes in one cluster.

Teardown (bin/down.sh)

  1. Delete the jbp namespace first and wait. This deletes the PVC, so the EBS CSI driver deletes its volume while the driver still exists. If the cluster goes first, the volume is orphaned and keeps billing.
  2. eksctl delete cluster --wait --disable-nodegroup-eviction. It deletes both stacks; skipping eviction saves minutes because nothing on the node needs a graceful drain.
  3. bin/leftovers.sh lists anything still billing: the cluster, eksctl-<name>-* stacks, and volumes tagged jbp-cluster. --delete removes orphaned volumes.

Teardown runs from a shell trap in all.sh, so it fires on success, on any failure (set -e), and on Ctrl-C. It doesn't fire if the laptop itself loses power. That is why leftovers.sh exists.

All live in the namespace jbp and are created by bin/run.sh. Templates use __VAR__ placeholders, filled from environment variables by a small Python render() in bin/common.sh.

Volume binding. The StorageClass uses WaitForFirstConsumer, so the EBS volume is created in the same availability zone as the node that runs the orchestrator. An EBS volume can't attach across zones.

4Orchestrator Job built

File: scripts/orchestrator.sh. Image: alpine/k8s:1.35.0, which already has bash, git, jq, kubectl and python3, so nothing gets installed at runtime. It requests 100m CPU and 128 Mi, so it barely takes space from the builds.

Loop, for each line of repos.txt

name url ref subdir overrides
 1. skip if results/<name>.json exists          (SKIP_DONE=1: resume after a spot reclaim)
 2. git clone --depth 1 [--branch ref] url /workspace/repos/<name>   (timed: clone_s)
    (a ref that isn't a branch/tag falls back to a full clone + checkout)
 3. detect.sh /workspace/repos/<name>/<subdir>  -> TOOL WRAPPER JAVA JAVA_SOURCE
    overrides in column 5 win: tool=gradle java=21
 4. pick_jdk:   smallest of SUPPORTED_JDKS (11 17 21 25) that is >= JAVA
 5. pick_image: maven -> MAVEN_IMAGE_<jdk>
                gradle + gradlew -> JDK_IMAGE_<jdk>   (wrapper brings its own Gradle)
                gradle, no wrapper -> GRADLE_IMAGE_<jdk>
 6. render build-job.tpl.yaml with sed, kubectl apply
 7. poll the Job every 5 s until succeeded>=1 or condition Failed=True
    (hard stop at BUILD_TIMEOUT_S + 10 min)
 8. save the Pod JSON (timeline) and the attempt count
 9. merge orchestrator facts + the build pod's <name>.build.json -> results/<name>.json

Why it's built this way

  • Clone in the orchestrator, build in a separate pod. That's your design. It also means build images need no git and no credentials, and clone time is measured apart from build time.
  • One by one by default (MAX_PARALLEL=1). Each build gets the whole CPU limit, so timings are clean and comparable between runs. With MAX_PARALLEL=N, cloning stays sequential while up to N builds run in the background (wait -n).
  • Polling instead of kubectl wait. kubectl wait can wait for one condition only, but here we need "Complete or Failed".
  • Results as files on the PVC, not in logs. They survive an orchestrator restart, which is what makes resume work.

The result record

results/<repo>.json combines what the orchestrator knows (url, commit, clone_s, repo_kb, tool, wrapper, java_required, java_source, jdk, image, pod_cpu, pod_mem, job_wall_s, ok) with what the build pod measured (rc, build_s, cpu_s, avg_cores, cpu_limit, throttled_pct, peak_mem_mib, oom_kills, tests, failures, errors, skipped, error_excerpt).

5Java + build tool detection built

File: scripts/detect.sh; tests: test/detect_test.sh (17 cases).

Tool: pom.xml means Maven, otherwise any build.gradle(.kts) or settings.gradle(.kts) means Gradle. If a repo has both, Maven wins unless tool=gradle is set. If mvnw or gradlew is present, it's used.

Java version, first hit wins:

  1. Explicit version files: .java-version, .sdkmanrc, .tool-versions, .mvn/jdk
  2. Maven, taking the highest value across all module poms: maven.compiler.release, then compiler-plugin <release>, then java.version (Spring Boot), maven.compiler.target, maven.compiler.source, <target>, .mvn/toolchains.xml
  3. Gradle: JavaLanguageVersion.of(N), jvmToolchain(N), options.release, JavaVersion.VERSION_N, sourceCompatibility, a java.version property
  4. Otherwise DEFAULT_JAVA (17)

Values are normalised: 1.8 becomes 8, 17.0.2 becomes 17, 21.0.1-tem becomes 21. The build runs on the smallest supported JDK at or above that number. Newer JDKs compile older targets through --release N, and picking the smallest keeps runtime behaviour, and Gradle-wrapper compatibility, closest to what the project expects.

This reads text with regexes; it doesn't evaluate the build. A version that comes from a parent POM in another repo, or that a Gradle script computes, falls back to the default. The report shows java_source so you can spot that, and java=N in repos.txt fixes it.

6Build Job built

Files: k8s/build-job.tpl.yaml, scripts/build.sh, config/images.env.

Pod spec

  • Image from images.env, by default pulled from public.ecr.aws/docker/library/. That's AWS's mirror of the Docker official images: no Docker Hub pull limit, and pulls stay inside AWS.
  • Resources: request = limit (default 2 CPU / 4 Gi). That gives Guaranteed QoS, matching how OpenShift build pods are usually sized, and the JVM sizes its heap and thread pools from the limit.
  • podAffinity to the orchestrator's node, because the EBS volume can attach to only one node.
  • backoffLimit: 0, activeDeadlineSeconds: BUILD_TIMEOUT_S, plus a podFailurePolicy. A pod killed by a spot reclaim (DisruptionTarget) is retried, and any non-zero exit fails the Job at once.

build.sh

maven : mvn|./mvnw -B -ntp -e -Dmaven.repo.local=/workspace/cache/m2 $MAVEN_ARGS_EXTRA ${MAVEN_GOALS:-verify}
gradle: gradle|./gradlew --no-daemon --console=plain $GRADLE_ARGS_EXTRA ${GRADLE_TASKS:-build}
        (GRADLE_USER_HOME=/workspace/cache/gradle when DEP_CACHE=shared)

Measurements, all read from the container's own cgroup (v2 on EKS AL2023, v1 fallback):

MetricSourceWhat it tells you
build_swall clock around the build commandThe number we optimise.
cpu_s, avg_corescpu.stat usage_usec delta ÷ wall timeHow much of the CPU limit the build actually used. Well below the limit means the build can't use the CPU (serial steps, I/O).
throttled_pct, throttled_scpu.stat nr_throttled / nr_periods, throttled_usecHow often the CFS quota stopped the build. High means it wants more CPU than the limit allows.

The full log goes to results/<repo>.build.log, and the report links it.

7Results collection + report built

When the orchestrator Job completes, run.sh starts jbp-collector on the same PVC, copies /workspace/results to runs/<RUN_ID>/results, saves nodes.json and run.env, and calls report/make_report.py, which uses only the Python standard library.

From each Pod's JSON the report also derives queue_s (pod created to scheduled: waiting for a node) and startup_s (scheduled to container started: image pull and volume attach). Output:

  • report.html: a single file with summary tiles, a stacked timeline per repo (clone, wait + pull, build), a per-repo table, a cost section and the run settings. Light and dark mode.
  • summary.csv: one row per repo, for comparing runs in a spreadsheet or notebook.

A sample from a local run is in samples/local-docker-report.html.

8Cost model + forecast built

File: report/make_report.py (cost()); prices in config/run.env.

Billed items

ItemDefault priceBilled for
EKS control planePRICE_EKS_HOUR=0.10The whole window from create start to delete end.
Spot node(s)PRICE_NODE_HOUR=0.07From node launch to termination, times NODE_COUNT.
EBSPRICE_EBS_GB_MONTH=0.08(nodes × node disk + PVC) GB × hours ÷ 730.
Public IPv4PRICE_IPV4_HOUR=0.005One per node, while it lives.
Not billednoneCloudFormation, data in, ECR Public pulls in-region, GitHub clones.

Measured cost (a run through bin/all.sh)

control_plane_s = down_end - up_start
node_s          = (down_start - up_end) + 6 min + 3 min
                  # nodes start ~6 min before up.sh returns, and die ~3 min into teardown
cost = 0.10 × cp_h + 0.07 × nodes × node_h + EBS + IPv4

Forecast (any run, even local Docker)

The work part is taken from the run itself (pipeline wall time, or the sum of clone + build when that's missing). Fixed overhead is added for an ephemeral EKS run:

control_plane_s = 18 min (up) + work + 3 min (collect) + 12 min (down)
node_s          =  6 min      + work + 3 min           +  3 min

Worked example, from the local test of your 6 repos plus 2 public ones (11:47 of work):

control plane  (18 + 11.8 + 3 + 12) min = 44.8 min × $0.10/h = $0.075
spot node      ( 6 + 11.8 + 3 +  3) min = 23.8 min × $0.07/h = $0.028
EBS            (40 + 30) GB × 0.4 h × $0.08/730              = $0.003
IPv4           0.4 h × $0.005                                = $0.002
                                                        total ≈ $0.11

What this tells us: about 70% of a small run is control plane time, and most of that is the ~30 minutes of create and delete. For short runs the cheapest lever is to batch more repos into one cluster, or keep it up with --keep across several experiment runs. Faster builds matter more once the work is longer than the overhead.

Spot prices change by region and hour. The defaults are typical us-east-1 numbers; check the EC2 spot pricing page and set PRICE_NODE_HOUR. The overhead constants (18/12/6/3 min) are estimates until the first real run measures them. Once it does, the measured cost replaces the forecast.

10Local modes

  • bin/local-docker.sh: no Kubernetes. The same orchestrator.sh runs on your machine with LAUNCHER=docker. Each build is a docker run of the same image and build.sh with --cpus/--memory set to the pod limits, and a local folder stands in for the PVC. It tests detection, images, builds and the report for free. This is how the pipeline was tested so far.
  • bin/local-kind.sh up|run|down: a real Kubernetes path on kind (Docker in Docker). It runs the exact manifests, RBAC and Job polling, with Docker Hub images and 1 CPU / 3 Gi pods. This is the free rehearsal before AWS.

11Optimisation experiment design designed, not built yet

Goal: find settings that cut build time, cost per build, or both, without changing the test result. That's the "correct feedback" requirement. The runner exists already (one run = one configuration). This section designs the layer that runs several configurations and compares them.

Method

  1. Baseline. Plain mvn -B verify, 2 CPU / 4 Gi, JVM defaults, dependency cache warm. Warm means a first run fills the cache and isn't measured; we're measuring build work, not Maven Central's speed.
  2. One factor at a time. Change a single setting per variant, against the same baseline, on the same node.
  3. Repeat and randomise. 3 repetitions per variant × repo, with variant order shuffled each round. Neighbour noise and spot node differences then spread evenly rather than biasing one variant.
  4. Correctness gate. A variant counts only if every repo passes with the same test count as the baseline. Fewer tests means it skipped work (e.g. a cache hit with no surefire reports, as seen in the earlier benchmark) and is flagged, not counted as faster.
  5. Combine the winners and re-measure the combination, since gains don't always add up.
  6. Re-run the winner cold (DEP_CACHE=none), the case a fresh OpenShift build pod actually sees.

Factors (from the earlier benchmark and the literature review)

Each variant reuses the existing runner with different environment variables, so nothing in the orchestrator changes. SKIP_DONE=0 and a fresh results/ per variant keep runs separate.

Comparison report (per repo × variant)

  • Median build_s and its range across reps; % change vs baseline. A change smaller than the baseline's own spread is called "no difference".
  • Cost per build = build_s × BUILD_CPU / node vCPUs × node $/h. The share of the node the pod reserves, which is how OpenShift capacity is paid for.
  • Correctness: test count equal to baseline (✓/✗), pass/fail.
  • avg_cores, throttled_pct and peak_mem_mib, to explain why a variant won or lost.

Budget

6 repos × ~8 min of work per variant pass × 6 variants × 3 reps ≈ 2.4 h of builds in one cluster. That's about 3 h of control plane and node time, roughly $0.50 to $0.60 for the whole matrix on spot, because the cluster is created only once.

12Known limits + open questions

  • The Kubernetes path hasn't run yet. kind can't start in the cloud sandbox used for development, so testing so far is local Docker plus static checks of the rendered YAML. First step: bin/local-kind.sh on a Mac, then one AWS run.
  • Single node / RWO volume. Parallel builds have to share one node. Spreading across nodes needs EFS (ReadWriteMany) or a volume per build.
  • Private repos need a token Secret mounted into the orchestrator (not wired yet).
  • Maven Central rate limits: at scale, put CodeArtifact or Nexus in front and point settings.xml mirrors at it.
  • OpenShift differences: OCP runs pods with a random UID (our stock images assume root for /workspace), uses Routes/SCCs, and often uses BuildConfigs or Tekton. Porting will need fsGroup or a writable-dir setup in the build pod.
  • Fixed overhead constants in the forecast are estimates until the first EKS run measures them.
