File map and call graph

The code splits into two halves. The driver runs wherever you type ./jbp and only talks to AWS and the Kubernetes API. The in-cluster half (orchestrator, detection, build script) is shipped into the cluster as ConfigMaps and runs inside stock images, so the project needs no image of its own.

jbp

Python, 9 linesEntry point

A tiny executable so you can type ./jbp all from the repo root. It puts pipeline/ on sys.path (the modules import each other by bare name, as they do inside the pod where they all sit in /app), imports main from cli, and exits with its return code.

sys.path.insert(0, str(Path(__file__).resolve().parent / "pipeline"))
from cli import main
sys.exit(main())

Calls cli.main

pipeline/cli.py

Python, 404 linesLogger name driverImports cluster, jbpcore

The driver. Each jbp subcommand maps to one cmd_* function. Commands that create or change something get a run folder runs/<RUN_ID>/ holding the driver log, the phase timestamps used for cost, and the collected results. Module constants: PIPE = ROOT/pipeline, RUNS = ROOT/runs.

class Runcli.py:38

One run's folder and its phase bookkeeping.

  • __init__(run_id=None): the id is the --run-id argument, else env RUN_ID, else a YYYYmmdd-HHMMSS timestamp. Creates runs/<id>/.
  • start_tracking(): attaches a StageTracker writing driver_status.json and driver_events.jsonl. Skipped for status/report, which only read.
  • phase(name, status="started", **kw): the one call every command uses to mark progress. It (1) updates the tracker, (2) appends <name>_start=<epoch> or <name>_end=<epoch> to phases.env (status started → start, ok/failed → end), and (3) logs a banner such as === UP STARTED. phases.env is what make_report.py reads to compute measured cluster time and cost.

effective_settings_text(cfg) → strcli.py:61

Serialises the merged settings (file + env overrides) back to KEY=value lines. Written to runs/<id>/settings.effective.env and shipped to the pod in the jbp-config ConfigMap, so BUILD_CPU=4 ./jbp run actually reaches the orchestrator. The report also prefers this file over config/settings.env.

k() · render() · apply() · configmap()cli.py:67-87

  • k(cfg, *args, **kw): kubectl -n <NAMESPACE> … through run().
  • render(path, values): reads a YAML template and replaces each __KEY__ with values[KEY]. Plain string replacement, no templating engine. See how templates are rendered.
  • apply(text): pipes YAML to kubectl apply -f - with 3 retries and a 120 s timeout. Everything is created through apply, so re-running a deploy is idempotent.
  • configmap(cfg, name, files): builds a ConfigMap with kubectl create configmap --dry-run=client -o yaml --from-file=key=path… and feeds the output to apply. The dry-run + apply trick turns "create" into "create or update".

run_on_cluster(cfg, r, repos) → boolcli.py:90

Deploys and runs one pipeline on the current kube context. Returns whether the orchestrator Job completed.

  1. Requires kubectl, logs the context. Builds the template values: all settings plus RUN_ID and STORAGE_CLASS_LINE (either storageClassName: X or an empty string, so the PVC falls back to the cluster default).
  2. DEPLOY: writes settings.effective.env; applies the namespace; creates three ConfigMaps: jbp-code (every pipeline/*.py + build.sh), jbp-config (repos file, images.env, effective settings), jbp-templates (build-job.tpl.yaml). Applies rbac.yaml and pvc.yaml.
  3. Cleans up the previous run: deletes the old jbp-orchestrator Job and jbp-collector Pod (waiting), and any Job labelled app=jbp-build. Job specs are immutable, so a re-run must delete before it applies.
  4. Applies orchestrator-job.yaml.
  5. ORCHESTRATE: follow_orchestrator(); phase is ok or failed.
  6. COLLECT: collect(), which runs even when the orchestrator failed, so partial results still reach the report.

follow_orchestrator(cfg, r) → boolcli.py:130

Shows the orchestrator's log live in the driver's console and decides when the run is over. Two loops run side by side:

  • Background thread stream(): polls pod_phase() (a jsonpath query for the newest pod's phase and waiting reason). While the pod is Pending it logs the reason (e.g. ContainerCreating). Once it is Running/Succeeded/Failed it runs kubectl logs -f job/jbp-orchestrator through run_streaming(raw=True), so the orchestrator's already-formatted lines print as-is with a   | prefix. If the stream drops (API hiccup, pod restarted after a spot reclaim), the loop reconnects.
  • Main loop: every 10 s reads the Job's conditions. Complete → True, Failed → False, more than 6 h → False. The Job status, not the log stream, is the source of truth.

Finally joins the thread (30 s max) and sets the done event.

collect(cfg, r, values)cli.py:180

  1. Applies collector-pod.yaml: a sleeping pod that mounts the PVC. The orchestrator pod has already exited, and a finished pod can't be kubectl cp'd from.
  2. Waits for it to be Ready (5 min), then kubectl cp jbp-collector:/workspace/results runs/<id>/results (2 retries).
  3. Deletes the pod without waiting, saves kubectl get nodes -o json to nodes.json (instance type, zone, capacity type for later analysis), and logs how many build logs came back.

make_report(r, cfg) → Path | Nonecli.py:195

Writes run.env (run id, kube context and the settings worth showing: CPU, memory, parallelism, cache mode, extra args, instance types, node count, region), then runs report/make_report.py as a subprocess. A bug in the report therefore can't break the driver, which matters because cmd_all calls it from the teardown path. Returns the report path, or None on failure (logged).

cmd_* command handlerscli.py:214-371

All take (cfg, r, args). They raise JbpError on failure, which main() turns into exit code 1.

main(argv=None) → intcli.py:374

  1. Builds the argparse tree: global -v/--verbose and --run-id; subcommands with their options (--repos defaults to config/repos.txt).
  2. Settings.load().
  3. For status and report: console logging only, no run folder. For everything else: a new Run, logging to the console and runs/<id>/driver.log, tracking on.
  4. Dispatches through a dict of handlers and times it. Exit codes: 0 success, 1 JbpError (message logged, no traceback), 130 Ctrl-C/SIGTERM. Any other exception propagates with a traceback, deliberately, because that is a bug.

pipeline/jbpcore.py

Python, 316 linesStandard library onlyUsed by cli, cluster, orchestrator

Everything shared between the driver and the orchestrator pod. It sticks to the standard library because the pod runs the stock alpine/k8s image, which has python3 but nothing installed with pip. ROOT is the repo root (parent of pipeline/).

now_ms() · utc_iso(ts=None) · fmt_duration(seconds)jbpcore.py:28-40

Epoch milliseconds; an ISO-8601 UTC string like 2026-11-15T11:38:01Z; and a human duration: 42s under a minute, m:ss above, - for None.

read_env_file(path) · class Settings(dict) · load_images()jbpcore.py:48-95

  • read_env_file: parses KEY=value lines with the regex _LINE; skips blanks and # lines; strips one pair of matching quotes. A missing file returns {}.
  • Settings.load(path=None, environ=None): reads config/settings.env (or path), then for every key already in the file takes the environment value if set. Only known keys can be overridden, so a stray env var can't sneak in. environ is injectable for tests.
  • Settings.int(key) / Settings.float(key): typed getters that raise ConfigError with the key name ("BUILD_TIMEOUT_S must be a whole number, got 'abc'") instead of a bare ValueError.
  • load_images(path, registry): reads images.env and substitutes {registry} with IMAGE_REGISTRY.

JbpError · ConfigError · CommandErrorjbpcore.py:100-112

JbpError is the base class for "expected" failures whose message is meant for a human; cli.main prints it without a traceback. CommandError(cmd, rc, stdout, stderr) keeps all four values and builds its message from the command (first 200 chars) plus the last 5 lines of stderr (or stdout), so a log line shows why a command failed, not just that it did.

setup_logging(component, logfile=None, verbose=False) · repo_logger()jbpcore.py:117-152

One format everywhere, in UTC:

2026-11-14T11:30:02Z INFO  orchestrator [perf-p2|DETECT] tool=maven java=21
  • _UTCFormatter uses time.gmtime and builds the [repo|STAGE] context from extra fields on the record.
  • Console handler at INFO (DEBUG with -v); file handler always at DEBUG, so every command line, rc and retry ends up in driver.log / orchestrator.log even when the console is quiet.
  • repo_logger(log, repo, stage) returns a LoggerAdapter carrying those extras. The orchestrator mutates rlog.extra["stage"] as a repo moves through CLONE → DETECT → … so every line is tagged with where it came from.

run(cmd, *, log, check=True, timeout, retries=0, backoff=5.0, input, env, cwd, retry_on=()) → CompletedProcessjbpcore.py:157

The single way the code runs kubectl, aws, git, docker.

  1. Logs the command at DEBUG (truncated to 500 chars), with the attempt number on retries.
  2. Runs it with captured text output. A timeout becomes a fake result with rc 124 (same as GNU timeout); a missing binary raises JbpError("command not found …").
  3. Returns on rc 0, or on any rc when check=False (the caller inspects returncode).
  4. Otherwise retries if attempts remain and, when retry_on is given, the output contains one of those substrings. The orchestrator uses this to retry git clone only on network errors, not on "repository not found". The delay doubles each time: 5 s, 10 s, 20 s….
  5. When out of retries, raises CommandError.

run_streaming(cmd, *, log, prefix="", timeout=None, env=None, raw=False) → intjbpcore.py:296

For long commands whose progress you want to see as it happens: eksctl create/delete cluster, kubectl logs -f, the local orchestrator. Merges stderr into stdout and reads line by line. Normal mode logs each line at INFO (so it gets the timestamp format). raw=True is for children that already log in our format: it prints the line unchanged and keeps a DEBUG copy in the file. Keeps the last 20 lines for the error message; kills the process past timeout; raises CommandError on a non-zero exit.

require_tools() · write_json_atomic() · read_json()jbpcore.py:197-220

  • require_tools(*tools): fails fast, naming every missing binary at once.
  • write_json_atomic(path, data): writes to a temp file in the same folder and os.replaces it into place. jbp status reads _status.json while the orchestrator rewrites it, so a reader must never see half a file.
  • read_json(path, default=None): returns default for a missing or corrupt file instead of raising.

class StageTracker (+ StageEvent)jbpcore.py:225-293

Records where a program is, for humans and for jbp status. Two files: a status file (current state, rewritten atomically on each change) and an events file (append-only JSON lines, the full history). The driver uses driver_status.json/driver_events.jsonl; the orchestrator uses results/_status.json/results/events.jsonl.

  • __init__(status_file, events_file, run_id, component): if the existing status file has the same run id, keeps its started time and per-repo state. That is how a restarted orchestrator pod (after a spot reclaim) continues the same picture instead of starting blank.
  • phase(name, status, **detail): sets the run-level phase.
  • repo(repo, stage, status, **detail): sets a repo's current stage/status, copies a whitelist of details (error, result, image, java, tool, attempt) and appends to the repo's history.
  • summary(): counts seen/finished/passed/failed and lists active repos with "STAGE since TIME".
  • A threading.Lock guards every write, because with MAX_PARALLEL > 1 several repo threads update it at once.

pipeline/cluster.py

Python, 209 linesLogger clusterCalled by cmd_up / cmd_down / cmd_leftovers

Creates and destroys the EKS cluster, and proves afterwards that nothing is still billing. Needs aws, eksctl, kubectl and AWS credentials. aws(cfg, *args) wraps aws --region <AWS_REGION> …; the explicit --region matters because awscli v1 ignores the AWS_REGION env var.

check_credentials(cfg) → str · cluster_exists(cfg) → boolcluster.py:23-34

check_credentials calls sts get-caller-identity so a bad or expired key fails in seconds, not 10 minutes into eksctl. It logs only the last 4 digits of the account id. cluster_exists is eks describe-cluster with check=False: rc 0 means it exists.

pick_version(cfg) → strcluster.py:37

If K8S_VERSION isn't auto, returns it. Otherwise asks eks describe-cluster-versions --version-status STANDARD_SUPPORT, sorts numerically (so 1.10 > 1.9) and takes the newest. A version in extended support bills the control plane at $0.60/h instead of $0.10/h.

available_instance_types(cfg) → list[str]cluster.py:52 PR #4

Filters INSTANCE_TYPES down to what the region really offers. eksctl only uses AZs that offer every listed type, so one missing type (m7a in ap-south-1) made creation fail with "only 0 zones discovered".

  1. ec2 describe-instance-type-offerings --location-type availability-zone for the wanted types → map type → set of AZs.
  2. Keep types offered in at least 2 AZs (EKS needs two); warn about the dropped ones; fail if none are left.
  3. Walk the kept types in order, intersecting AZ sets, and keep a type only if the running intersection still has ≥ 2 AZs. The result is a list whose common AZs satisfy eksctl.

up(cfg, tracker=None)cluster.py:119

  1. check_credentials.
  2. If the cluster exists, reuse it (makes --keep + repeated runs cheap). Otherwise: pick_version, available_instance_types, write eksctl_config to a temp file, and run_streaming eksctl create cluster -f with a 1 h timeout, each eksctl line logged with an eksctl: prefix. Failure raises a JbpError telling you jbp down cleans up partial stacks.
  3. aws eks update-kubeconfig to point kubectl at it.
  4. Applies storageclass-eks.yaml with __CLUSTER_NAME__ filled in.
  5. Logs each node's instance type, capacity type (SPOT) and zone.

down(cfg) → boolcluster.py:151

  1. check_credentials. If the cluster exists:
  2. Update kubeconfig and delete the jbp namespace first, waiting up to 5 min. That deletes the PVC while the EBS CSI driver still runs, so the driver deletes the volume. If the cluster went first, the volume would be orphaned and keep billing. Failure here is only a warning; the leftovers check catches the volume.
  3. eksctl delete cluster --wait --disable-nodegroup-eviction (45 min timeout). Skipping eviction saves minutes because nothing on the node needs a graceful drain. Errors are logged, not raised, so verification still runs.
  4. Returns wait_until_clean().

leftovers(cfg) → dict · wait_until_clean(cfg, timeout_s=1200, every_s=30) → bool · delete_orphan_volumes(cfg)cluster.py:182-222

  • leftovers returns a dict with any of: cluster (still exists), stacks (CloudFormation stacks named eksctl-<name>-* in a live or failed state), volumes (EBS volumes tagged jbp-cluster=<name>). Empty dict means clean.
  • wait_until_clean is the poller: calls leftovers every 30 s for up to 20 min, logging what is still present. On timeout, logs each item as STILL BILLING plus how to fix it, and returns False.
  • delete_orphan_volumes deletes tagged volumes in state available (not attached to anything). Used by jbp leftovers --delete.

cost(cp_s, node_s) → dictmake_report.py:104

Cost lines for given control-plane seconds and node seconds:

control plane = PRICE_EKS_HOUR  × cp_hours
spot nodes    = PRICE_NODE_HOUR × nodes × node_hours
EBS           = (nodes × NODE_DISK_GB + PVC_SIZE) × PRICE_EBS_GB_MONTH / 730 × node_hours
public IPv4   = PRICE_IPV4_HOUR × nodes × node_hours
  • Actual (only when both up and down were measured): control plane from up_start to down_end; nodes from up_end to down_start plus 6 min (nodes start before up ends) and 3 min (they die early in teardown).
  • Projected: a typical ephemeral run of this workload, 18 min up + builds + 3 min collect + 12 min down.

HTML and CSV outputmake_report.py:125-263

  • fmt(), mmss(): number and duration formatting; cost_table(): a card per cost dict.
  • An inline SVG of stacked bars per repo: clone | wait + pull | build (green pass / red fail), scaled to the slowest repo.
  • A table row per repo (result, tool, Java needed and where that came from, image, times, tests, average cores vs limit, throttled %, peak memory vs limit, log link), plus a red error row with failure_kind, message and the build's error_excerpt for failures.
  • The page is one %-formatted string, which is why the CSS inside it writes 100%%.
  • summary.csv gets a fixed column list (repo, passed, tool, java, image, commit, clone/queue/startup/build seconds, tests, CPU, throttling, memory, OOM kills, attempts).

pipeline/orchestrator.py

Python, 470 linesLogger orchestratorRuns in the orchestrator Job or via jbp local-dockerImports detect, jbpcore

The heart of a run. For each repo, one by one: CLONE → DETECT → LAUNCH → WAIT → COLLECT → DONE/FAILED. Every stage change goes to results/_status.json and results/events.jsonl. Two rules shape the code: a failing repo never stops the run, and a restarted pod resumes where the last one stopped.

parse_repos(path) → (list[RepoSpec], list[str])orchestrator.py:52

Parses repos.txt. Per line: drop comments; split on whitespace; need at least name url. The remaining tokens without = are positional ref and subdir (- means default). Tokens with = are overrides: tool=maven|gradle, java=N. Problems (too few fields, unknown override, duplicate name) are collected, not raised: the bad line is skipped and main() logs a warning, so one typo doesn't sink the run.

RepoSpec · Plan · Outcome (dataclasses)orchestrator.py:42-106

launch_and_wait(spec, plan, rlog, tracker) → Outcome:

  1. Render, save a copy as results/<repo>.job.yaml (so you can see exactly what ran), delete any old Job with that name, apply with 3 retries. Stage → WAIT.
  2. Every 5 s, read the Job and its pods as JSON. If the API can't be read, count it; 12 in a row (~1 min) → Outcome(infra).
  3. Decide:
    • status.succeeded ≥ 1 → ok.
    • Condition Failed → timeout if reason is DeadlineExceeded (the Job's activeDeadlineSeconds), else build.
    • Older than BUILD_TIMEOUT_S + 600 → timeout (a safety net in case the Job never reports).
    • Otherwise ask _pod_problem(); log the note when it changes, so the log shows "unschedulable → pulling → running" without repeating itself every 5 s.
  4. Save the newest pod as results/<repo>.pod.json (the report derives queue and image-pull time from it). attempts = number of pods, since a spot reclaim makes the Job start a new pod.
  5. For image, unschedulable and infra failures, delete the Job so it stops retrying in the background.

k8s/storageclass-eks.yamlStorageClass jbp-gp3

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata: {name: jbp-gp3}
provisioner: ebs.csi.aws.com
volumeBindingMode: WaitForFirstConsumer
reclaimPolicy: Delete
parameters:
  type: gp3
  tagSpecification_1: "jbp-cluster=__CLUSTER_NAME__"
  • provisioner ebs.csi.aws.com: the EBS CSI driver installed as an eksctl add-on. EKS ships with no default StorageClass, which is why the PVC needs this one.
  • volumeBindingMode: WaitForFirstConsumer: the EBS volume isn't created until a pod using the PVC is scheduled. EBS volumes live in one AZ; creating it immediately could put it in an AZ with no node, and the pod could never mount it.
  • reclaimPolicy: Delete: deleting the PVC deletes the EBS volume. That's what makes "delete the namespace first" in down() free the volume.
  • type: gp3: cheaper than gp2 with a 3000 IOPS baseline regardless of size.
  • tagSpecification_1: tags each volume jbp-cluster=<name>, which leftovers() searches for.

k8s/orchestrator-job.yamlJob jbp-orchestrator

spec:
  backoffLimit: 0

    rules:
      - action: Ignore                    # spot reclaim: rerun, finished repos are skipped
        onPodConditions: [{type: DisruptionTarget}]

    spec:
      serviceAccountName: jbp-orchestrator
      restartPolicy: Never
      containers:
        - name: orchestrator

          command: [python3, -u, /app/orchestrator.py]
          env: LAUNCHER=k8s, RUN_ID, SETTINGS_FILE=/config/settings.env,
               IMAGES_FILE, REPOS_FILE, TEMPLATE=/templates/build-job.tpl.yaml, WORKSPACE=/workspace

          volumeMounts: /workspace (PVC), /app (jbp-code), /config (jbp-config), /templates (jbp-templates)
  • backoffLimit: 0: a real failure (the Python process exits non-zero) fails the Job at once; no blind retries.
  • podFailurePolicy with DisruptionTarget → Ignore: when Kubernetes evicts the pod (spot reclaim, node drain, preemption) it sets the DisruptionTarget condition.   • No activeDeadlineSeconds: the run length depends on the repo list; the driver gives up after 6 h instead.
  • Code from a ConfigMap: /app holds orchestrator.py, detect.py, jbpcore.py and build.sh, so a stock image runs the project's logic without building or pushing an image.

  • Resources: tiny request (it mostly sleeps and polls), a 512Mi memory limit as a guard, no CPU limit so it is never throttled.
  • The pod label app: jbp-orchestrator is what the build Jobs' podAffinity targets.

k8s/build-job.tpl.yamlJob jbp-build-<repo>

spec:
  backoffLimit: 0
  activeDeadlineSeconds: __TIMEOUT__      # BUILD_TIMEOUT_S
  podFailurePolicy:
    rules:
      - action: Ignore                    # spot reclaim / drain: retry, not counted
        onPodConditions: [{type: DisruptionTarget}]
      - action: FailJob                   # build.sh exited non-zero: fail now
        onExitCodes: {operator: NotIn, values: [0]}
  template:
    spec:
      restartPolicy: Never
      affinity:
        podAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector: {matchLabels: {app: jbp-orchestrator}}
              topologyKey: kubernetes.io/hostname
      containers:
        - name: build
          image: __IMAGE__                # chosen by pick_image()
          imagePullPolicy: IfNotPresent
          command: [bash, /app/build.sh]
          env: REPO_NAME, TOOL, WRAPPER, JAVA, WORKDIR, RESULT_DIR, DEP_CACHE, MAVEN/GRADLE_ARGS_EXTRA
          resources:
            requests: {cpu: __CPU__, memory: __MEM__}
            limits:   {cpu: __CPU__, memory: __MEM__}
          volumeMounts: /workspace (PVC), /app (jbp-code, read-only)
  • activeDeadlineSeconds: Kubernetes kills the pod and fails the Job with reason DeadlineExceeded after BUILD_TIMEOUT_S; launch_and_wait maps that reason to failure_kind=timeout.
  • podFailurePolicy: rules are checked in order. An eviction (DisruptionTarget) is ignored, so the Job starts a fresh pod and the report shows the extra attempt. Any non-zero exit from build.sh is a real build failure and fails the Job immediately with no retry, since a deterministic failure would just fail again.
  • podAffinity on app=jbp-orchestrator with topologyKey: kubernetes.io/hostname: "schedule this pod on the same node as a pod labelled app=jbp-orchestrator". The PVC is ReadWriteOnce and already attached to the orchestrator's node, so a build pod anywhere else could never mount it. required… makes it a hard rule; …IgnoredDuringExecution means it is only checked at scheduling time. If the node can't fit the pod, it shows as Unschedulable, and _pod_problem fails it after UNSCHEDULABLE_GRACE_S.
  • requests = limits: gives the pod Guaranteed QoS, the same shape as an OpenShift build pod. The CPU limit becomes the cgroup CFS quota that build.sh reads as cpu_limit and whose throttling it measures; the JVM also sizes its thread pools from it.
  • imagePullPolicy: IfNotPresent: the second repo on the same JDK reuses the image already on the node.
  • Job labels jbp/run and jbp/repo tie each Job to a run; app: jbp-build lets the driver delete them all before a new run.

tests/

Run with python3 -m unittest discover -s tests (39 tests, under a second, no cluster or network). The two YAML tests skip if PyYAML isn't installed.

tests/test_detect.py — DetectTest (25 tests)

Each test writes a throwaway repo into a temp dir with repo(name, files) and asserts tool, Java version and source with check(). Covers: maven.compiler.release, source 1.8, Spring's java.version, compiler-plugin <release>, ${property} resolution, a property from a local parent POM, highest module wins, nothing declared → 17, unresolvable property noted, broken XML noted but not fatal, .java-version/.sdkmanrc/.mvn/jdk precedence, wrapper detection, Gradle toolchain / jvmToolchain (kts) / sourceCompatibility / JavaVersion.VERSION_17 and VERSION_1_8 / release, settings.gradle only, both builds present, forced Gradle, unknown, and normalise() edge cases.

tests/test_orchestrator.py (14 tests)

  • ParseReposTest: a full line with ref/subdir/overrides, dashes and comments, problems collected not raised, and that the shipped config/repos.txt parses cleanly.
  • K8sLauncherTest: Job names are DNS-safe and ≤ 63 chars; render() leaves no __X__ placeholder; _pod_problem fails ImagePullBackOff and Unschedulable only after their grace periods (by back-dating bad_since), and treats Running as fine.
  • TrackerTest: status and events files are written, the summary counts are right, and a second tracker with the same run id keeps the earlier repo state (resume).
  • SettingsTest: env overrides the file; images.env has all three images for every supported JDK.
  • ManifestTest: every k8s YAML renders with no leftover placeholder and parses with apiVersion, kind, metadata.name.
  • ClusterConfigTest: eksctl_config() is valid YAML with spot on, NAT disabled, six instance types and the requested version.

Things worth knowing

Found while writing this page. None of them breaks a run; they are candidates for a small clean-up PR.

  • The report's "tries" column always shows 1. K8sLauncher stores attempts in results/<repo>.json, but make_report.py (line 70-71) overwrites it with the contents of a <repo>.attempts file that nothing writes any more (a leftover of the earlier shell version), falling back to 1. So a build that survived a spot reclaim isn't flagged in the report.
  • Report footer wording. The report says prices come from "config/run.env"; they come from settings.env / settings.effective.env.
  • The PVC name is fixed in three places. pvc.yaml, orchestrator-job.yaml and collector-pod.yaml hard-code jbp-workspace, while K8sLauncher.render reads an optional PVC_NAME. Setting PVC_NAME alone would point build Jobs at a claim that doesn't exist.
  • Orchestrator.run returns 0 even when every repo fails, by design: the orchestrator Job is Complete and the failures show in the report. jbp run exits non-zero only if the orchestrator itself crashed.
